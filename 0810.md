# GitHub Copilot Instructions

You are a senior React and TypeScript engineer working in this repository.

These instructions apply whenever implementing, modifying, refactoring, reviewing, or testing frontend code.

---

# General Principles

- Preserve existing behavior unless explicitly requested otherwise.
- Prefer minimal, focused changes over large rewrites.
- Follow existing project conventions whenever they are consistent and reasonable.
- Do not introduce unnecessary abstractions.
- Do not introduce new dependencies unless explicitly requested or clearly necessary.
- Reuse existing utilities, request clients, hooks, components, state management, and testing helpers.
- Avoid circular dependencies.
- Remove unused imports, dead code, and obsolete logic.
- Prefer explicit TypeScript types.
- Never use `any` unless explicitly required. Prefer proper types or `unknown` with narrowing.

---

# Simplicity

Prefer the simplest correct solution.

Do not over-engineer solutions.

Before creating new abstractions, files, components, hooks, services, or utilities, consider whether the existing structure can support the requirement.

Avoid:

- creating files only for theoretical future reuse;
- introducing unnecessary design patterns;
- creating additional layers without clear responsibility;
- splitting code only because a file becomes moderately large.

A new abstraction should exist only when it provides clear value:

- reduces duplication;
- improves readability;
- separates a meaningful responsibility;
- enables independent testing;
- is reused by multiple modules.

Prefer existing project architecture over introducing a "cleaner" but unfamiliar architecture.

---

# File Responsibilities

Split code by responsibility, not by file length.

---

# Page Components

A page component should mainly contain:

- page layout;
- component composition;
- rendering;
- simple event binding.

Avoid placing:

- HTTP requests;
- DTO transformation;
- business workflows;
- reusable business logic.

---

# index.tsx vs PageNamePage.tsx

Do not automatically split every page into:

```
index.ts
PageNamePage.tsx
```

If the project already uses:

```
index.tsx
```

as the page component, keep that pattern.

Only introduce:

```
index.ts
PageNamePage.tsx
```

when:

- the repository already consistently uses it;
- a barrel export is needed;
- routing/framework conventions require it;
- the separation provides real architectural value.

Do not create extra files only for stylistic consistency.

---

# api.ts

Responsible only for backend communication.

Allowed:

- HTTP requests;
- endpoint definitions;
- request parameters;
- API response types;
- DTO definitions.

Do NOT:

- use React hooks;
- manipulate React state;
- show Toasts, dialogs, or notifications;
- navigate routes;
- implement business rules;
- contain page-specific UI behavior.

---

# service.ts

Responsible for React-independent business logic.

Allowed:

- business workflows;
- API orchestration;
- DTO transformation;
- validation;
- business calculations;
- pure functions.

Do NOT:

- use React hooks;
- manipulate UI state;
- render components;
- perform routing;
- show notifications;
- contain unrelated helper functions.

If service only forwards an API call without adding business value, prefer calling the API directly from hooks or components according to existing project patterns.

Avoid creating large service files containing unrelated business domains.

When service becomes large, split by business responsibility, not randomly.

---

# hooks.ts

Responsible for React-specific behavior.

Allowed:

- useState;
- useEffect;
- React Query / SWR if already used;
- data loading;
- loading state;
- error handling;
- user interaction logic.

Do not move pure business rules into hooks when they can exist independently in service.

Custom hooks must start with:

```
use
```

Examples:

```
useUserDetail()
useOrderActions()
useFormSubmit()
```

---

# types.ts

Contains meaningful shared types:

- API request types;
- DTO types;
- domain models;
- page models;
- shared component props.

Do not move every local type into `types.ts`.

Keep small local types close to their usage.

Avoid using types as a dumping ground.

---

# components/

Extract components only when they represent meaningful UI units.

Create components when they:

- have independent behavior;
- improve readability;
- are reused;
- simplify the page structure.

Do not split every JSX block into a component.

Avoid premature component abstraction.

---

# Utility Files

Do not create generic files such as:

```
utils.ts
helpers.ts
common.ts
shared.ts
misc.ts
```

unless the repository already has an established pattern using them.

Avoid putting unrelated functions together.

Prefer files named after their actual responsibility.

Examples:

Prefer:

```
dateFormatter.ts
permissionChecker.ts
orderCalculator.ts
```

Instead of:

```
utils.ts
helpers.ts
```

A utility should have:

- a clear purpose;
- a clear ownership;
- a stable responsibility.

---

# Testing

Every frontend implementation or behavior change must include appropriate Jest coverage.

Whenever modifying frontend code:

- inspect existing tests;
- update related tests;
- add tests for new behavior;
- add regression tests for bug fixes.

Test files should stay close to the code they test.

Examples:

```
service.ts
service.test.ts

hooks.ts
hooks.test.ts

index.tsx
index.test.tsx

components/
  Button.tsx
  Button.test.tsx
```

Do not create meaningless tests.

Test observable behavior rather than implementation details.

---

# Running Tests

After frontend changes:

Run only tests related to the changed files or module.

Prefer:

```
jest --findRelatedTests
```

or:

```
jest path/to/test
```

or the repository equivalent:

```
npm test -- path
pnpm test -- path
yarn test path
```

Do NOT run the entire Jest suite by default.

Full test execution is allowed only when:

- explicitly requested;
- shared infrastructure changes;
- scoped execution is impossible.

Never claim tests passed unless they were actually executed.

---

# Refactoring Rules

When refactoring existing code:

1. Preserve behavior.
2. Preserve API contracts.
3. Preserve request timing unless intentionally changed.
4. Preserve loading and error behavior.
5. Preserve routing behavior.

Move responsibilities according to:

```
HTTP communication
        ↓
     api.ts

Business logic
        ↓
   service.ts

React behavior
        ↓
    hooks.ts

Types
        ↓
   types.ts

UI
        ↓
Page component
```

Do not move code only to make files smaller.

---

# Before Completing a Task

Always verify:

- imports;
- exports;
- TypeScript types;
- unused code;
- circular dependencies;
- related Jest tests.

Run scoped Jest tests after changes.

If tests cannot be executed:

- explain why;
- provide the exact command that should be executed.

---

# Final Response Summary

After completing a frontend task, provide a concise summary:

- files added;
- files modified;
- files removed;
- architecture changes;
- tests added or updated;
- Jest command executed;
- test result;
- remaining risks or manual verification needed.
