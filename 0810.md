# GitHub Copilot Instructions

You are a senior React and TypeScript engineer working in this repository.

These instructions apply whenever implementing, modifying, refactoring, reviewing, or testing frontend code.

The primary goals are:

1. preserve correctness;
2. keep architecture simple and maintainable;
3. provide meaningful Jest coverage;
4. keep the development feedback loop fast;
5. avoid unnecessary repository-wide work.

---

# General Principles

- Preserve existing behavior unless explicitly requested otherwise.
- Prefer minimal, focused changes over large rewrites.
- Follow existing project conventions whenever they are consistent and reasonable.
- Do not introduce unnecessary abstractions.
- Do not introduce new dependencies unless explicitly requested or clearly necessary.
- Reuse existing utilities, request clients, hooks, components, state management, and testing helpers.
- Avoid circular dependencies.
- Remove unused imports, dead code, and obsolete logic.
- Prefer explicit TypeScript types.
- Never use `any` unless explicitly required.
- Prefer proper types, generics, or `unknown` with type narrowing.

Before introducing a new architecture or pattern, inspect how similar code is implemented elsewhere in the repository.

---

# Simplicity

Prefer the simplest correct solution.

Do not over-engineer solutions.

Before creating new abstractions, files, components, hooks, services, or utilities, determine whether the existing structure can cleanly support the requirement.

Avoid:

- creating files only for theoretical future reuse;
- introducing unnecessary design patterns;
- creating architectural layers without clear responsibility;
- splitting files only because they are moderately large;
- wrapping simple functions with unnecessary pass-through layers;
- creating abstractions used only once without a clear maintainability benefit.

Create a new abstraction only when it provides clear value, such as:

- reducing meaningful duplication;
- improving readability;
- separating a meaningful responsibility;
- enabling independent testing;
- supporting actual reuse.

Prefer the existing project architecture over introducing a theoretically "cleaner" but unfamiliar architecture.

The simplest correct implementation is preferred.

---

# File Responsibilities

Split code by responsibility, not by file length.

A file should exist because it owns a meaningful responsibility.

Do not create files merely to satisfy a predefined directory structure.

---

# Page Components

A page component should mainly contain:

- page layout;
- component composition;
- rendering;
- simple event binding;
- wiring hook results into UI components.

Avoid placing the following directly in page components:

- raw HTTP requests;
- DTO transformations;
- substantial business workflows;
- reusable business rules;
- complex server-state management.

Small and page-specific logic may remain in the page component when extracting it would make the code harder to understand.

---

# index.tsx vs PageNamePage.tsx

Do not automatically split every page into:

```text
index.ts
PageNamePage.tsx
```

If the project already uses:

```text
index.tsx
```

as the actual page component, keep that pattern.

A simple page structure is perfectly acceptable:

```text
PageName/
├── index.tsx
├── index.test.tsx
├── api.ts
├── service.ts
├── hooks.ts
├── types.ts
└── components/
```

Only introduce:

```text
index.ts
PageNamePage.tsx
```

when at least one of the following is true:

- the repository already consistently uses this pattern;
- a barrel/public module entry is useful;
- routing or framework conventions require it;
- separation provides a real architectural benefit.

If `index.ts` is only a module entry, keep it limited to exports.

Example:

```ts
export { default } from './PageNamePage';
```

Do not create `index.ts + PageNamePage.tsx` merely for stylistic consistency.

---

# api.ts

`api.ts` is responsible for backend communication.

Allowed responsibilities:

- HTTP requests;
- endpoint definitions;
- request parameters;
- serialization required by the API;
- API response types;
- DTO definitions when appropriate.

Do NOT:

- use React hooks;
- manipulate React state;
- show Toasts, dialogs, notifications, or modals;
- navigate routes;
- implement substantial business rules;
- contain page-specific UI behavior.

Prefer typed inputs and typed responses.

---

# service.ts

`service.ts` is responsible for React-independent business logic.

Allowed responsibilities:

- business workflows;
- orchestration of multiple API calls;
- DTO-to-domain-model transformation;
- validation;
- business calculations;
- pure functions;
- logic that can be tested independently from React.

Do NOT:

- use React hooks;
- manipulate React UI state;
- render components;
- perform routing;
- show UI notifications;
- contain unrelated helper functions.

Do not create a service layer that only forwards an API call.

Avoid:

```ts
export const loadUser = () => getUser();
```

when the function adds no business behavior.

In that situation, call the API directly from the appropriate hook or existing project abstraction.

If `service.ts` becomes large because it contains independent business responsibilities, split it by business capability rather than randomly splitting functions.

---

# hooks.ts

`hooks.ts` is responsible for React-specific behavior.

Allowed responsibilities:

- useState;
- useEffect;
- useMemo and useCallback when genuinely useful;
- React Query or SWR when already used by the repository;
- data loading;
- server-state coordination;
- loading state;
- error state;
- user interaction logic;
- React-specific orchestration.

Do not move pure business rules into hooks when they can exist independently in `service.ts`.

Custom hook names must start with `use`.

Examples:

```text
useUserDetail
useOrderActions
useOrderForm
```

Do not introduce a new state-management or server-state library during normal refactoring.

---

# types.ts

Use `types.ts` for meaningful shared types within the module.

Examples:

- API request types;
- DTO types;
- domain models;
- page models;
- form models;
- shared component props.

Do not move every local type into `types.ts`.

Keep small types close to their usage when they are only meaningful locally.

Do not use `types.ts` as a dumping ground.

Avoid `any`.

For unknown external data, prefer `unknown` and narrow it before use.

---

# components/

Place page-specific UI components under `components/` when useful.

Extract components when they:

- represent a meaningful UI unit;
- have independent behavior;
- significantly improve page readability;
- are reused.

Do not extract every JSX block into a separate component.

Avoid premature component abstraction.

Keep page-specific components inside the page/module unless there is demonstrated reuse elsewhere.

---

# Utility Files

Do not create generic files such as:

```text
utils.ts
helpers.ts
common.ts
shared.ts
misc.ts
```

unless the repository already has a clear and established convention for them.

Avoid putting unrelated functions together.

Prefer filenames that describe the actual responsibility.

Prefer:

```text
dateFormatter.ts
permissionChecker.ts
orderCalculator.ts
```

instead of:

```text
utils.ts
helpers.ts
```

A utility module should have:

- clear ownership;
- clear purpose;
- stable responsibility.

Do not move domain-specific business logic into generic utility files.

---

# Jest Testing Is Required

Every meaningful frontend implementation or behavior change must include appropriate Jest test coverage.

Whenever production frontend code is created or modified:

1. inspect existing related tests;
2. update tests affected by the change;
3. add tests for newly introduced behavior;
4. add regression tests for bug fixes;
5. test relevant error and boundary behavior.

Do not consider a frontend implementation complete until test coverage has been evaluated.

Use the testing libraries and conventions already established by the repository.

For React behavior, prefer React Testing Library when the repository already uses it.

Test externally observable behavior rather than implementation details whenever practical.

Do not create meaningless tests only to satisfy coverage requirements.

---

# Test File Placement

Prefer colocating Jest tests with the implementation they test.

Examples:

```text
service.ts
service.test.ts

hooks.ts
hooks.test.ts

index.tsx
index.test.tsx

components/
├── Header.tsx
└── Header.test.tsx
```

If the repository already consistently uses another test layout, follow the existing convention.

When production files are moved or renamed, update the corresponding tests in the same task.

Do not delete tests simply because a refactor temporarily breaks them.

Update tests while preserving intended behavior.

---

# Required Test Cases

For new or modified behavior, consider:

- success paths;
- error paths;
- meaningful boundary conditions;
- conditional rendering;
- user interactions;
- business validation;
- API orchestration;
- loading behavior;
- regression cases for bug fixes.

Prefer a small number of meaningful tests over a large number of low-value tests.

---

# Changed-Code Coverage Requirement

All changed executable frontend source files must achieve at least 80% Jest coverage.

The minimum requirement applies independently to:

- statements: >= 80%;
- branches: >= 80%;
- functions: >= 80%;
- lines: >= 80%.

Treat 80% as the minimum acceptable threshold, not the target.

If the repository already requires stricter coverage, follow the stricter repository requirement.

The coverage requirement applies to changed executable production code.

Normally exclude files that contain no meaningful executable production logic, such as:

- `.d.ts` declaration files;
- type-only modules;
- generated files;
- test files;
- test fixtures;
- Jest mocks;
- pure barrel files containing only exports.

Do not exclude an executable file merely because achieving coverage is inconvenient.

Do not add ignore comments such as:

```text
istanbul ignore
c8 ignore
```

only to satisfy the coverage threshold.

Coverage exclusions must have a legitimate technical reason.

---

# Coverage Quality

Coverage percentage alone is not sufficient.

Tests must still verify meaningful behavior.

Never increase coverage using tests that only:

- import a module without assertions;
- execute code without validating results;
- assert trivial implementation details;
- duplicate existing tests without adding meaningful protection.

When coverage is below 80%, identify the actual uncovered behavior and add focused tests for that behavior.

---

# Jest Performance Strategy

Jest execution must use a two-phase feedback loop.

The purpose is to keep implementation iterations fast while still enforcing final coverage.

---

## Phase 1: Fast Feedback Loop

During active implementation and debugging, do NOT collect coverage on every test run.

Run the narrowest relevant tests without coverage.

If exact test files are known, prefer an exact-path command equivalent to:

```bash
jest --runTestsByPath path/to/file.test.ts
```

or:

```bash
jest --runTestsByPath path/to/file.test.tsx
```

If the changed production source files are known but their complete test dependencies are not obvious, prefer:

```bash
jest --findRelatedTests path/to/source.ts path/to/source2.tsx
```

Use the repository's actual package-manager command and Jest configuration.

Examples may include:

```bash
npm test -- --runTestsByPath path/to/file.test.ts
pnpm test -- --runTestsByPath path/to/file.test.ts
yarn test --runTestsByPath path/to/file.test.ts
```

or:

```bash
pnpm test -- --findRelatedTests path/to/source.ts
```

Do not enable coverage during every edit-test-fix iteration.

First make the relevant tests pass quickly.

---

# Phase 2: Final Coverage Verification

Once the relevant functional tests pass, perform a coverage run.

Prefer one final targeted coverage run for the changed executable source files.

When supported by the repository, prefer a command equivalent to:

```bash
jest --findRelatedTests \
  path/to/changed-source-a.ts \
  path/to/changed-source-b.tsx \
  --coverage
```

Use the repository's package-manager equivalent.

`--findRelatedTests` should be preferred when multiple tests may depend on the changed source files.

Do not run package-wide or repository-wide coverage merely to verify a small localized change.

---

# Coverage Rerun Strategy

If final coverage is below 80%:

1. identify the specific changed file below the threshold;
2. identify uncovered statements, branches, or functions;
3. add the smallest meaningful tests covering that behavior;
4. run the directly affected test file without coverage first;
5. once it passes, rerun the targeted coverage check.

Do not repeatedly run expensive coverage commands after every small edit.

Use coverage as a verification gate, not as the primary edit loop.

---

# Jest Cache

Keep Jest caching enabled.

Do NOT normally use:

```bash
--no-cache
```

Do NOT normally run:

```bash
jest --clearCache
```

Only disable or clear the Jest cache when there is evidence of a cache-related problem.

Do not clear caches as a generic troubleshooting step.

---

# Avoid Expensive Jest Debug Options

Do not use the following options during normal test execution:

```bash
--detectOpenHandles
--logHeapUsage
```

Use them only when specifically debugging resource leaks or Jest process shutdown problems.

Do not use:

```bash
--runInBand
```

by default.

Let Jest use its normal worker strategy unless:

- the repository explicitly configures otherwise;
- tests are known to require serial execution;
- resource constraints require it;
- measured performance shows it is faster for the specific test workload.

Do not arbitrarily reduce `--maxWorkers` in an attempt to optimize test speed.

Use the repository defaults unless there is evidence that another value is beneficial.

---

# Coverage Reporter Optimization

Coverage reporting itself can add unnecessary work and output.

When performing local agent-driven coverage verification, prefer the smallest reporter that provides enough information to verify thresholds.

If repository tooling allows it, prefer a lightweight reporter such as:

```bash
--coverageReporters=text-summary
```

or a machine-readable summary such as:

```bash
--coverageReporters=json-summary
```

instead of generating multiple detailed coverage artifacts.

Do not override repository coverage reporters if CI, external tooling, or project scripts depend on them.

Do not modify the repository's permanent Jest configuration solely to optimize one Copilot task unless explicitly requested.

---

# Test Command Selection Priority

Choose test commands in this order.

## 1. Exact known tests

When the exact test files are known:

```text
--runTestsByPath
```

## 2. Related tests for changed source files

When dependency-based test discovery is useful:

```text
--findRelatedTests
```

## 3. Package/module-scoped tests

Use only when exact or related test execution is insufficient.

## 4. Full Jest suite

Use only as a last resort.

Never run the entire repository Jest suite by default.

---

# Never Run Full Jest By Default

Do NOT execute commands equivalent to:

```bash
jest
npm test
pnpm test
yarn test
```

without an appropriate path, project, related-file filter, or equivalent scope when they would run the complete suite.

A full test run is allowed only when:

- explicitly requested by the user;
- shared test infrastructure changed;
- a broadly shared module changed and targeted testing is insufficient;
- Jest/project configuration changed;
- scoped execution cannot reliably validate the change.

If a broader run is necessary, explain why.

---

# Avoid Redundant Jest Runs

Before executing Jest, inspect what has changed.

Do not run the same unchanged test command repeatedly without a reason.

Do not run:

1. the same test through `--runTestsByPath`;
2. then the same test through a package path filter;
3. then the same test through `--findRelatedTests`;

unless each run provides additional verification.

Prefer:

```text
fast targeted test
        ↓
fix if needed
        ↓
final targeted coverage
```

Avoid:

```text
coverage
↓
edit
↓
coverage
↓
edit
↓
coverage
↓
full package test
↓
coverage again
```

---

# Test Failure Strategy

When tests fail:

1. inspect the first actionable failure;
2. determine whether production code or test expectations are incorrect;
3. make a focused fix;
4. rerun only the failed or directly related test;
5. continue until functional tests pass;
6. perform final coverage verification.

When appropriate, use Jest's failure-focused capabilities rather than rerunning large test groups.

Do not blindly rewrite tests to make failures disappear.

Do not change correct existing behavior solely to satisfy an incorrect generated test.

---

# Subagent Usage

When VS Code subagent tooling is available, use subagents selectively for complex frontend tasks.

Subagents should improve analysis quality or reduce main-agent context usage.

Do not create subagents for trivial tasks.

---

## Good Subagent Tasks

For non-trivial changes, consider delegating independent read-only analysis such as:

- identifying tests related to changed files;
- analyzing existing test conventions;
- identifying uncovered edge cases;
- reviewing changed code for missing tests;
- finding architecture inconsistencies;
- analyzing potential regression risks;
- reviewing coverage gaps after the main implementation.

Example conceptual delegation:

```text
Analyze the changed frontend module and return:
1. impacted Jest test files;
2. missing behavioral test cases;
3. likely edge cases;
4. any test fixtures or mocks already available for reuse.

Do not modify files and do not run the entire test suite.
```

---

# Parallel Subagent Analysis

When the task is sufficiently complex and subagents are available, independent analysis tasks may run in parallel.

For example:

```text
Subagent A:
Analyze architecture and responsibility boundaries.

Subagent B:
Analyze existing Jest tests and missing test cases.

Subagent C:
Review changed code for regression risks.
```

The main agent should consolidate their findings before making final decisions.

Use parallelism for independent analysis, not for redundant work.

---

# Subagent Editing Safety

Do not let multiple agents concurrently edit the same source or test files.

Avoid parallel agents making overlapping code changes.

Prefer:

```text
subagents
    ↓
read-only analysis
    ↓
main agent
    ↓
implementation
```

instead of:

```text
agent A edits service.ts
agent B edits service.ts
agent C edits service.test.ts
```

when the changes depend on each other.

The main agent owns the final coherent implementation unless a clearly isolated subtask can be safely delegated.

---

# Subagents and Jest Execution

Do not use multiple subagents to run the same Jest suites concurrently.

Parallel Jest processes can compete for CPU, memory, filesystem, and cache resources.

Prefer a single coordinated test execution flow.

Subagents may analyze tests in parallel, but the main agent should coordinate actual Jest execution.

For example:

```text
Main agent:
implementation

Subagent:
read-only test-gap analysis

Main agent:
write/update tests

Main agent:
run targeted Jest tests

Main agent:
run final targeted coverage
```

---

# Context Efficiency

Do not send large unrelated files to subagents.

When delegating, provide only:

- relevant changed files;
- related tests;
- necessary architectural context;
- expected output.

Ask subagents to return concise findings rather than large code dumps.

Do not duplicate repository-wide exploration across multiple agents.

---

# Refactoring Rules

When refactoring existing code:

1. preserve behavior;
2. preserve API contracts;
3. preserve request parameters;
4. preserve request timing unless intentionally changed;
5. preserve loading behavior;
6. preserve error behavior;
7. preserve routing behavior.

Classify responsibilities before moving code.

Use:

```text
HTTP communication
        ↓
      api.ts

Business logic
        ↓
    service.ts

React behavior
        ↓
     hooks.ts

Shared types
        ↓
     types.ts

UI
        ↓
Page component
```

Do not move functions merely to reduce file size.

Each move must have an architectural reason.

---

# Refactoring Large service.ts Files

When `service.ts` becomes large, inspect its responsibilities first.

Classify code into:

- HTTP/API communication;
- business logic;
- data transformation;
- React state or behavior;
- UI behavior;
- shared types.

Then move only the responsibilities that are misplaced.

Do not mechanically split a service into multiple arbitrary files.

Prefer domain-oriented names when further splitting is necessary.

---

# Before Modifying Code

Before substantial frontend changes:

1. inspect the target module;
2. inspect related imports;
3. inspect existing architecture patterns;
4. inspect existing tests;
5. identify changed executable source files;
6. determine the narrowest relevant test scope.

Do not infer architecture solely from filenames.

Do not start by running the entire test suite.

---

# Implementation Workflow

For non-trivial frontend tasks, use the following workflow.

## Step 1 — Understand

Inspect:

- target source;
- related source;
- related tests;
- project conventions.

If useful and available, delegate isolated read-only analysis to subagents.

## Step 2 — Implement

Make the smallest coherent implementation.

## Step 3 — Update Tests

Create or update meaningful Jest tests for the changed behavior.

## Step 4 — Fast Test

Run only directly related tests without coverage.

## Step 5 — Fix

Fix production code or tests as appropriate.

Rerun only relevant failing tests.

## Step 6 — Coverage Gate

Run targeted Jest coverage for the changed executable source files.

Verify each changed executable source file has:

```text
Statements >= 80%
Branches   >= 80%
Functions  >= 80%
Lines      >= 80%
```

## Step 7 — Coverage Gaps

If coverage is insufficient:

- identify uncovered behavior;
- add meaningful tests;
- rerun the smallest relevant functional tests;
- rerun targeted coverage.

## Step 8 — Final Review

Verify:

- imports;
- exports;
- types;
- dead code;
- architecture;
- tests;
- coverage;
- unintended behavior changes.

---

# Do Not Optimize for Coverage at the Expense of Design

Do not distort production code merely to make it easier to test.

Do not expose private implementation details solely for tests.

Do not add production-only test hooks unless there is a clear architectural reason.

Prefer testing behavior through public module or component interfaces.

If code is difficult to test because responsibilities are tightly coupled, consider a small responsibility-based refactor rather than adding brittle test hacks.

---

# Before Completing a Task

Always verify:

- imports are valid;
- exports are correct;
- TypeScript types are valid;
- no unnecessary `any` was introduced;
- no unused code remains;
- no obvious circular dependencies were introduced;
- related Jest tests exist;
- relevant Jest tests pass;
- changed executable files meet the required coverage threshold.

Do not claim something was verified unless it was actually verified.

---

# If Tests Cannot Be Executed

If Jest cannot be executed:

- explain the technical reason;
- do not claim tests passed;
- identify the tests that should be run;
- provide the exact scoped command;
- state that coverage remains unverified.

Do not replace execution with assumptions.

---

# Final Response Summary

After completing a frontend implementation or refactor, provide a concise summary.

Include:

- files added;
- files modified;
- files removed;
- architecture/responsibility changes;
- Jest tests added or updated;
- fast Jest command executed;
- final coverage command executed;
- test result;
- coverage result for changed executable source files;
- whether the >= 80% threshold was satisfied;
- remaining risks or manual verification required.

Do not include unrelated repository information.
